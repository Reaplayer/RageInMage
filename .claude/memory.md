## Controller support regressions — bootstrap deadlock (FIXED & PIE-confirmed 2026-07-04) + chord-spell no-release (CODE WRITTEN 2026-07-04, pending Live Coding compile + PIE test)
Two separate controller bugs found/fixed this session. Both edits are function-body/template-body only (no member/signature/layout changes) → Live Coding hot-patchable, no full rebuild needed.
1. **Bootstrap deadlock (FIXED, Reaper confirmed "the controller was working" + spells firing).** Controller couldn't move the character or fire at all. Root cause in `RageInMagePlayerController.cpp`: `BeginPlay` only added `IMC_MAKContext` (priority 0), which has ZERO gamepad mappings. `IMC_ControllerContext` (left-stick→IA_Move, right-stick→IA_Look, triggers/buttons→abilities) was added only inside `UpdateControllerIMC()` and only once `bUsingGamepad` was already true — but `bUsingGamepad` flips true ONLY in `Look()`, which fires only from `IA_Look` = `Gamepad_Right2D`, a mapping that lives ONLY in the never-added controller context. Total chicken-and-egg: the context that detects the gamepad can't activate until the gamepad is detected. (Even the saved-keybinding path `ApplyControllerCustomKeybindings` was gated behind the same `bControllerIMCActive` flag, so it couldn't bootstrap it either.) Regressed from the documented original design (Architecture Notes ~line 543: "Both IMCs active simultaneously"). **Fix:** `BeginPlay` now adds `ControllerMageContext` at priority 1 and sets `bControllerIMCActive = true`, BEFORE `LoadAndApplyKeybindings()` (so the runtime-rebind swap still works — sees the flag true and swaps in the runtime copy). The two contexts map disjoint physical keys (keyboard/mouse vs `Gamepad_*`) so both-active is conflict-free. `UpdateControllerIMC()` gutted to a no-op (comment retained) — it used to tear the controller context down on M&K switch, which would re-create the deadlock in reverse (couldn't switch back to gamepad because right-stick Look lives in the torn-down context). Device detection (`bUsingGamepad`) still drives cursor visibility / aim mode / which InputConfig+IMC the UI reads for key icons — just no longer touches mapping contexts. Assets were all fine (both IMCs exist; all `BP_RageInMagePlayerController` defaults assigned). NOTE UE5.8: IMC key mappings now live under `DefaultKeyMappings.Mappings` (legacy top-level `Mappings` array reads empty via NeoStack `array_count` — not a bug, runtime reads DefaultKeyMappings fine).
2. **Chord spells aim but never release (CODE WRITTEN, pending compile+test).** Controller chord abilities (modifier LB + button, e.g. LB+RT = Ultimate; Defensive/CrowdControl are the other `InputTriggerChordAction` entries in `IMC_ControllerContext`) activate and show their hold-to-aim indicator but never fire. Activation flows through `Triggered`/Held (`AbilityInputTagHeld`→TryActivate + sets `Spec.InputPressed=true`); release flows ONLY through `Completed` (`AbilityInputTagReleased`→clears `Spec.InputPressed`). The `AimMode` task (`RageInMageAbilityTask_AimMode.cpp`) polls `Spec->InputPressed` each tick and fires `OnInputReleased` when it goes false. But a chord-triggered action fires **`ETriggerEvent::Canceled`, NOT `Completed`**, when the chord breaks on release — and `BindAbilityActions` (`RageInMageEInputComponent.h` template) only bound `Completed→ReleasedFunc`. So chord releases were dropped, `InputPressed` stayed true forever. Plain Pressed triggers (M&K + non-chord controller) emit `Completed` normally → they worked. **Fix:** added a second `BindAction(..., ETriggerEvent::Canceled, ..., ReleasedFunc, Action.InputTag)` alongside the Completed binding. Harmless for non-chord bindings (Pressed triggers don't emit Canceled). **NOT yet PIE-tested.** If still broken, WATCH: possible separate issue — RT is shared by IA_Ability_Secondary (no chord) AND IA_Ability_Ultimate (chord), so LB+RT may double-fire Secondary unless a `UInputTriggerChordBlocker` is on the non-chord action (Reaper didn't report double-fire, so blockers are probably configured — but verify Secondary doesn't also trigger). **Chord fix PIE-CONFIRMED working by Reaper 2026-07-04.**
3. **Gamepad aim reworked to a velocity-driven virtual cursor (CODE WRITTEN 2026-07-04, pending compile+test; MAY NEED FULL REBUILD — new members added).** Evolved over two passes this session:
   - Pass A (superseded): removed the `* StickMagnitude` scaling so aim was pure DIRECTION at fixed `AimProjectionDistance`. Killed the original snapback (magnitude scaling had dragged the point toward the caster as the stick eased off) but Reaper found "point a direction → instantly max range" too twitchy/imprecise.
   - Pass B (current): right stick now drives a **persistent virtual cursor** — stick deflection is a VELOCITY that moves the cursor, not an absolute direction. Stored as `FVector2D AimCursorOffset` (a LOCAL XY offset from the caster), integrated each Tick: `AimCursorOffset += camRelative(GamepadAimInput) * AimCursorSpeed * DeltaTime`, clamped to `AimProjectionDistance`. World aim = `PawnLocation + offset`; because it's caster-relative it keeps its screen position as the character moves (mouse-cursor-pinned-to-caster feel). Releasing the stick stops integrating → cursor holds (no snapback). Z resolved by tracing straight DOWN the cursor column (ECC_Visibility, ignores the pawn) → snaps aim onto ground/objects and highlights an enemy under the cursor. `CursorTrace()` now early-returns after `GetHitResultUnderCursor` when `bUsingGamepad` (keeps CursorTraceHit fresh for the mouse-move → M&K switch-back detection, but skips the M&K highlight so the gamepad virtual-cursor highlight owns it). NEW members in `RageInMagePlayerController.h`: `FVector2D AimCursorOffset` (plain) + `UPROPERTY(EditDefaultsOnly,"Aim") float AimCursorSpeed = 1500.f` (units/sec at full stick — tune to taste). **Because new members change class layout, Live Coding may reject with C2065 (the documented inconsistent gotcha) — if it does, close editor + full `Build.bat` rebuild.**
   - Pass C (current): the virtual cursor is now MODAL — only active while aiming a spell. Reaper wanted normal movement to keep the simple direction+snapback so turning/dodging stay tight. Added `bool bAimingSpell` (private) + public `BeginGamepadAim(float InitialReach)` / `EndGamepadAim()`. The `AimMode` ability task (`RageInMageAbilityTask_AimMode.cpp`) calls `BeginGamepadAim(MaxRange)` in `Activate()` and `EndGamepadAim()` in `OnDestroy()` (task already includes the PC header for GetClampedAimPosition). `BeginGamepadAim` seeds `AimCursorOffset` = caster forward × min(MaxRange, AimProjectionDistance) so the spell starts aimed where the character faces, not on itself. In `UpdateAimDirection`'s `bUsingGamepad` branch: `if (bAimingSpell)` → virtual cursor (velocity, no snapback, Z-trace, highlight); `else if (past deadzone)` → ORIGINAL magnitude-scaled direction `Origin + AimDir * AimProjectionDistance * StickMagnitude` (snapback restored for facing/dodge). Files: `RageInMagePlayerController.cpp` (UpdateAimDirection split + BeginGamepadAim/EndGamepadAim + CursorTrace guard), `RageInMagePlayerController.h` (`bAimingSpell` + 2 methods + AimCursorOffset/AimCursorSpeed), `RageInMageAbilityTask_AimMode.cpp` (Activate/OnDestroy hooks).

## SparkingSphere over-damage fix — per-target cooldown model (CODE WRITTEN 2026-07-02, NEEDS FULL REBUILD, not yet compiled/tested)
**Symptom (Reaper):** SparkingSphere (Lightning Secondary) "kills WAAAAY too quickly" — appeared to damage all actors in range every frame. **Root cause:** SparkingSphere's damage is 100% inherited from base `ARageInMageZone`, which has TWO damage sources that double-dip on a *moving* zone: (1) `OnZoneOverlap` hits each actor immediately on entry, AND (2) a global timer (`DamageTickEnemiesInside` every `DamageTickInterval`) hits everyone currently inside on one synchronized schedule. Moving sphere gliding through a crowd → entry hit + near-immediate synchronized timer hit + repeated. **Reaper's desired model:** check every frame who's in range, damage an actor only if it hasn't been damaged within `DamageTickInterval` (per-target independent cooldown), NOT a global every-0.5s nuke.
**Fix (scoped so the 3 other zone subclasses + Meteor/Surf/ChargedSpell/Yoyo that share the base are UNAFFECTED):** Added `virtual bool ARageInMageZone::UsesBuiltinTickDamage() const { return true; }` to the base — when true (every existing zone), behaviour is unchanged; when false, base BeginPlay skips the timer AND OnZoneOverlap skips the immediate on-entry damage (both gated on it). Also added base helper `void ApplyDamageSpecToActor(AActor*) const` (DRY'd the two existing apply sites). `ARageInMageSparkingSphereZone` overrides `UsesBuiltinTickDamage()`→false and drives damage in its `Tick()`: each frame `ZoneCollision->GetOverlappingActors(_, APawn::StaticClass())`, and for each valid non-instigator non-friendly actor, if `!LastDamageTimeByActor.Contains(Actor) || Now - last >= DamageTickInterval` → `ApplyDamageSpecToActor` + record `Now`. Cooldown map is `TMap<TWeakObjectPtr<AActor>, float>` (weak so dead actors fall out safely; pruned each tick). New-in-range actor has no timestamp → immediate first hit, then silent for the interval. Ability's `DamageTickInterval` default = 0.5f (confirmed in header).
**Files:** `RageInMageZone.h/.cpp` (new virtual + helper + gated timer/overlap damage), `RageInMageSparkingSphereZone.h/.cpp` (override + TMap + Tick damage). **NEEDS FULL `Build.bat` REBUILD** — new virtual = vtable change on an already-loaded base + new member on subclass; Live Coding cannot hot-patch (per the established gotcha). Not yet compiled or PIE-tested. IceZone's `DamageTickEnemiesInside` slow/freeze override + Fire/Water base-damage zones are untouched (they keep the builtin timer path).

### Ceaseless Wrath (Lightning Ultimate) — C++ ability class written (NOT yet compiled, no asset exists yet)

### Knockback Momentum Transfer + Bounce-Off-Immovable System (DONE)
**User request:** Pushback/knockback currently just stops dead the instant a launched character collides with another actor. Wanted: if the target can absorb it, transfer some momentum to the target and slow (not stop) the original; if the target can't be moved, bounce off it instead.
**New `Poise` secondary attribute** added to `URageInMageAttributeSet` (replicated, `OnRep_Poise`, gameplay tag `Attributes.Secondary.Poise`, added to `TagsToAttributes` map). Defaults to 0 for everyone — purely an additive bonus meant to come from gear (no GEs grant it yet; that's on the user to design/itemize later). Explicitly NOT the existing `ImmovableMass` attribute — user clarified that's a separate Earth-mage stacking/CC-overload mechanic (charges when standing still, decays when moving/dashing, breaks at 100% total slow) unrelated to general knockback resistance.
**New shared `ARageInMageCharacterBase::ApplyKnockbackImpulse(Impulse, bXYOverride, bZOverride)`** — scales the impulse down by `100/(100+TargetPoise)` then calls `LaunchCharacter`. **Refactored all 8 existing direct `LaunchCharacter` call sites to route through it** so the behavior is uniform everywhere: `RageInMageDamageGameplayAbility::ApplyKnockback`, `RageInMageConeBlastAbility::ApplyConeBlast`, `RageInMageLeapAbility::ApplyLandingExplosion`, `RageInMageSurfAbility::SurfDamageCheck`, `RageInMageProjectile.cpp`'s anonymous-namespace `ApplyKnockbackToActor`, `RageInMageYoyoProjectile::OnSphereOverlap`, and both call sites in `RageInMageWaveBox::ProcessEnemyOverlaps` (drag + vertical pop). **New `ARageInMageCharacterBase::NotifyHit` override** (fires for free on any blocking-hit during character movement — confirmed via engine source `UPrimitiveComponent::DispatchBlockingHit`/`AActor::DispatchBlockingHit`, no special collision flags needed for kinematic character sweeps). Logic, gated to `bSelfMoved && HasAuthority()` and a per-actor-pair 0.2s de-dupe (sliding/multi-sweep can fire `NotifyHit` several times per frame):
- Ignored entirely if horizontal speed < `MinKnockbackTransferSpeed` (default 300) — keeps normal AI-pathing bumps from triggering this.
- Target resistance = `BaseShoveResistance` (400) + `OtherPoise * PoiseResistancePerPoint` (5/pt) if the other actor is a character; **infinite** (`TNumericLimits<float>::Max()`) if it's anything else (walls/static geometry always "win").

## Tooling Gotchas (NeoStack Lua bridge)

### Adding a field to a USTRUCT used inside a UDataAsset array wipes that array's data in the live session
**Recurring issue, confirmed by the user as something they've hit before** (not new to this session): adding a new `UPROPERTY` field to a `USTRUCT` that's used as the element type of a `TArray<Struct>` on a `UDataAsset` (e.g. adding `StunImmunityGraceSeconds` to `FRageInMageConditionInfo`, used by `UConditionInfo::ConditionInfos`), then recompiling (Live Coding in this instance, but the user says plain IDE recompiles have done this too), can wipe that array back to empty-default elements **in the live editor session** — the struct's old serialized data doesn't survive the layout change. Confirmed via `a:get('ConditionInfos')` going from real data (Burning/Frozen/OverCharged/Charged rows) to `((),(),(),...)` (all empty) immediately after the recompile, with no `save()` call made in between.
**Not necessarily true data loss** — as long as nothing calls `save()` on the affected asset before reloading, the on-disk `.uasset` should still have the original data; the wipe is only in the in-memory copy. User's existing workflow: expect this, and manually re-enter the affected data asset's rows after this kind of struct change (confirmed they've done this before and are fine doing it again).
**Mitigation for future sessions:** before adding a new field to any USTRUCT already used inside a `TArray`/`TMap` on a `UDataAsset`, warn the user this may wipe that asset's array data on next recompile, and confirm they're OK re-entering it (or get the current values first via `get()` so they can be manually restored) rather than assuming Live Coding will safely preserve it.
**Confirmed recovery path (validated this session, Flash And Awe stun-immunity work):** the wipe is in-memory only as long as the affected asset is never saved in that wiped state. Close the editor WITHOUT saving the wiped data asset, do a full `Build.bat`/restart rebuild (not Live Coding), reopen — the asset reloads from its still-intact on-disk `.uasset` with all original rows AND the new struct field both present. No manual re-entry needed if you catch it before saving.

### `load_level()` discards unsaved in-editor changes — silent data-loss risk
Calling `load_level(path)` reloads the level fresh from the saved `.umap` on disk, silently discarding any unsaved in-memory edits — it is NOT a safe "just open this to inspect it" operation if the level might already be open with unsaved work. This actually happened: the user had placed enemies in `Tournament_Forest_2` that were only ever captured in an editor autosave (`Saved/Autosaves/Game/Maps/Tournament_Forest_2_Auto1.umap`, newer + larger than the saved `.umap`), and a `load_level()` call (done to check nav bounds) wiped them from the editor. The autosave file still exists on disk and could have been used to recover (load it, then save-as over the real path) — user opted to skip recovery and re-place enemies manually instead. **Before calling `load_level()`, check `playtest_status()`/current level state first; prefer inspecting the already-open level directly (`select_all_actors()` + `get_selected_actors()`) over reloading it.**

### New native gameplay tags don't register until the editor restarts
Adding a new tag to `FRageInMageGameplayTag` (e.g. `Condition_StunImmune` this session) compiles fine via Live Coding — `class_properties`/`class_methods` on other new symbols in the same compile confirm the module genuinely hot-patched. But the new tag itself is **not usable** in the running session: `FRageInMageGameplayTag::Get()` almost certainly lazy-initializes via a `static bool bInitialized` guard that already ran once before the edit, so the new `AddNativeGameplayTag()` call never executes this session. Symptom: any editor-script attempt to set a `FGameplayTag`/`FGameplayTagContainer` property to the new tag's name silently produces an *empty* container (the string fails to parse against the tag manager) — easy to mistake for a tool/property-set bug rather than an unregistered tag. Confirmed by testing: setting the same struct shape with a pre-existing tag (`Condition.Frozen`) round-tripped fine on the same asset/property in the same script. **Fix: full editor restart** (this is a distinct flavor of the existing "Live Coding can't hot-patch new class members" gotcha below — same root cause category (static init not re-run), different symptom).

### GameplayEffect tag-granting uses GEComponents in UE 5.8, not the legacy struct fields — and the scripting tool can't add them
`InheritableGameplayEffectTags`/`InheritableOwnedTagsContainer` (the old `FInheritedTagContainer` struct fields on `UGameplayEffect`) can be *read* via `class_properties`/`a:get()` and even *appear* to `a:set()` successfully (the immediate `a:get()` echoes back the new value) — but the change is silently wiped the moment the asset is saved/compiled. Root cause: existing GE assets in this project (e.g. `GE_Frozen`) actually grant their tags via `GEComponents` sub-objects (`TargetTagsGameplayEffectComponent` for granted/owned tags, `AssetTagsGameplayEffectComponent` for asset tags) — confirmed by reading `GE_Frozen.GEComponents`, which contains exactly those two component instances. The legacy struct fields are vestigial and get reset on save/compile for assets that use the modern component model. **The NeoStack scripting tool has no way to add `GEComponents`** — `a:add_component(name, class)` only accepts actor/scene component types ("Class not found or not a component type" for `TargetTagsGameplayEffectComponent`), and there's no dotted-path or raw-export-text way to instantiate a new sub-object into the `GEComponents` array. **Workaround: add these two components by hand in the editor** (Details panel → Components → Add Component → "Target Tags" / "Asset Tags", then set the tag on each) for any new GameplayEffect Blueprint that needs to grant a tag. Worth reporting on the Betide Studio Discord as a gap in GameplayEffect authoring support.

### Live Coding cannot hot-patch new class members
`exec_command('LiveCoding.Compile')` (equivalent to Ctrl+Alt+F11 in-editor) reliably patches **function-body-only** changes (e.g. the `IsBothEnemy` null-check fix) but fails on changes that add/remove `UPROPERTY`/`UFUNCTION` members or change class layout/size — even though UHT reruns and the header is correct, you get `error C2065: '<new member>': undeclared identifier`. Adding a new property to an existing UCLASS needs a full editor restart + normal `Build.bat`/UBT compile. Also note: `Build.bat` itself refuses to run at all while the editor is open with Live Coding active ("Unable to build while Live Coding is active") — the editor must be closed first.

## Architecture Notes

### Controller Input Flow
Both IMCs active simultaneously but share the same `IA_Ability_*` InputAction assets. Only ONE `BindAbilityActions()` call is made (using M&K config/tags). Each ability spec carries both M&K and Controller tags via DynamicSpecSourceTags. The M&K tag is used for ability activation; controller tags exist only for UI display (key icons). `InputTagToControllerInputTag` mapping: LMB→Controller.LT, RMB→Controller.RT, Shift→Controller.RB, 1→A, 2→B, 3→X, 4→Y.

### Keybinding System
- M&K bindings: `IMC_MAKContext` -> `DA_MAKInputConfig` -> M&K InputTags
- Controller bindings: `IMC_ControllerContext` -> `DA_ControllerInputConfig` -> Controller InputTags
- Runtime remapping creates a duplicate IMC, modifies key mappings, swaps contexts
- Persistence via `RageInMageSettingsSaveGame` (separate maps for M&K and controller)
- `ControlsWidgetController` exposes `GetAllBindings()` / `GetAllControllerBindings()` for UI
